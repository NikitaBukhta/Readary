# Internationalization (i18n)

The app ships with three UI languages — English, Russian, Ukrainian —
selectable at runtime from the Profile/Settings page. The pipeline that
gets us there has three moving parts:

```
Source code              translate command            Runtime
─────────────              ───────────────────              ──────────
qsTr / tr in     ──►   buildtools/commands/   ──►   QTranslator inside
.cpp/.hpp/.qml         translate.py (Python):       LanguageModel:
                       1) regex-scan sources          .qm loaded from
                       2) auto-translate via          qrc:/i18n/library_<lang>.qm
                          deep-translator             on language change
                       3) write translations/         engine->retranslate()
                          library_<lang>.ts           + Loader.active toggle
                       4) lrelease → .qm
```

## Runtime layer

### `bl::models::LanguageModel`

[src/models/settings/LanguageModel.hpp](../../src/models/settings/LanguageModel.hpp)

- `Q_ENUM Code { English = 0, Russian = 1, Ukrainian = 2 }`
- `Q_PROPERTY current` (R/W) — the active code, persisted to `QSettings`
  under `ui/language` (`QGuiApplication::organizationName/applicationName`
  set in `main.cpp` anchor it to a stable per-user location).
- `Q_PROPERTY available` (CONSTANT, `QList<int>`) — supported codes.
- `Q_INVOKABLE label(code)` — display name for a code (`"English"`,
  `"Русский"`, `"Українська"`).
- `Q_INVOKABLE localeCode(code)` — short locale string (`"en"` / `"ru"` /
  `"uk"`) used to load the matching `.qm`.
- `applyCurrent()` — `removeTranslator(_translator)` →
  `_translator->load(":/i18n/library_<code>.qm")` →
  `installTranslator(_translator)`. Logs a warning when the .qm is
  missing (fresh checkout without `translate` run).
- `defaultCode()` — picks Russian/Ukrainian/English from `QLocale().name()`
  on first launch.

`QML_ELEMENT + QML_UNCREATABLE` — registered so QML can read enum values
(`SettingsController.languageModel.Russian`) but can't instantiate it
directly. The controller owns the single instance.

### `bl::controllers::SettingsController`

[src/controllers/SettingsController.hpp](../../src/controllers/SettingsController.hpp)

Thin façade — a QML singleton that composes settings models. Today it
only owns `LanguageModel`; future preference areas (theme, fonts, sync)
plug in as additional `Q_PROPERTY` members of the same controller, so
QML always reaches them through `SettingsController.<area>`.

```cpp
Q_PROPERTY(bl::models::LanguageModel *languageModel READ languageModel CONSTANT FINAL)
```

QML usage:

```qml
SettingsController.languageModel.current === SettingsController.languageModel.Russian
SettingsController.languageModel.available           // [0, 1, 2]
SettingsController.languageModel.label(code)         // "English" / "Русский" / "Українська"
SettingsController.languageModel.current = code      // setter, persists + retranslates
```

### `AppInitializer` wiring

[src/core/AppInitializer.cpp](../../src/core/AppInitializer.cpp)

```cpp
_settingsController = new controllers::SettingsController(this);
_settingsController->languageModel()->applyCurrent();        // initial load
connect(_settingsController->languageModel(),
        &models::LanguageModel::currentChanged, this,
        [this] { _engine->retranslate(); }, Qt::QueuedConnection);
```

Two reasons for `Qt::QueuedConnection`:

- `currentChanged` fires inside the QML setter that triggered the change,
  so a *synchronous* `retranslate()` would run on the same call stack as
  the binding evaluation that just changed `current`. Bindings on the
  active page wouldn't re-evaluate until the setter returned.
- Queued posting defers `retranslate()` to the next event-loop iteration —
  the QML setter completes, dependent bindings refresh, then translation
  runs on a clean stack.

### Loader-driven page refresh (`Main.qml`)

[qml/Main.qml](../../qml/Main.qml)

`QQmlEngine::retranslate()` reliably refreshes simple direct
`text: qsTr("…")` bindings, but in Qt 6.x it does **not** re-evaluate
`qsTr()` calls nested inside object literals stored in `var` properties
(e.g. `_navItems` arrays of `{ label: qsTr(…) }` entries). The page
content also lives behind a `Loader`, and active-page bindings can stay
stale until the loader rebuilds them.

The robust fix:

```qml
readonly property var _retranslatableLoaders: [pageLoader, bottomNavBarLoader]

Connections {
    target: SettingsController.languageModel
    function onCurrentChanged() {
        for (let i = 0; i < root._retranslatableLoaders.length; ++i) {
            root._retranslatableLoaders[i].active = false;
            root._retranslatableLoaders[i].active = true;
        }
    }
}
```

- Both the page (`pageLoader`) and the footer (`bottomNavBarLoader` —
  `BottomNavBar` is wrapped in a `Loader` whose `sourceComponent` is
  declared inline) are toggled `active = false → true`. The `source` /
  `sourceComponent` bindings stay intact, so navigation keeps working.
- New `Loader` instantiations evaluate `qsTr()` against the
  *already-installed* new `QTranslator`, so all strings come out in the
  new language.
- Adding another retranslatable area later = appending its `Loader` to
  `_retranslatableLoaders` — no per-component plumbing.

### Default Settings page entry

`PROFILE_PAGE` in `NavigationController` currently routes to the
[Settings page](../../qml/pages/settingsPage/SettingsPage.qml), where
the language list is rendered as a `Repeater` over
`SettingsController.languageModel.available`. Tapping a language sets
`languageModel.current = …` directly.

## Build / authoring layer

### `python bootstrap.py translate`

[buildtools/commands/translate.py](../../buildtools/commands/translate.py)

Self-contained Python pipeline — does **not** call `lupdate`. The
vcpkg `qttools` port only ships `lupdate-pro.exe` (qmake-project mode)
which silently skips QML when fed a plain source-file list, so we own
the scan instead.

1. **Scan** — recurse `src/` for `.cpp/.hpp` and `qml/` for `.qml/.js`.
   Regex captures `tr(...)`, `qsTr(...)`, `QT_TR_NOOP`,
   `QT_TRANSLATE_NOOP`, with optional disambiguation comment and
   plural-count argument. C++ context is derived as
   `<namespace>::<class>` from the file's namespace declarations and
   first `class X` (matches what runtime `tr()` would use). QML context
   is the file basename (matches Qt's runtime convention).
2. **Auto-translate** — `_Translator` wraps
   `deep_translator.GoogleTranslator(source="en", target=<ru|uk>)`.
   Lazy import; on the first run the pipeline pip-installs
   `deep-translator` into the project venv and patches `sys.path` so
   the system Python that runs `bootstrap.py` can import it.
   Placeholders `%1`, `%n`, `%L1`, … are sentinelized
   (`@@PH0@@`) before the call and restored after, so Google's mangler
   doesn't eat them. Translations are cached in-memory per run.
3. **Preserve manual edits** — `_read_existing(ts_path)` parses the
   prior `.ts`, keeps every `<translation>` that is non-empty AND not
   `type="unfinished"`. Re-running `translate` won't overwrite curated
   strings; it only fills in new entries.
4. **Write** `translations/library_<lang>.ts` in Qt-Linguist 2.1 XML.
   English uses identity translations.
5. **Compile** to `.qm` via `lrelease` (resolved by
   [`LinguistProvider`](../../buildtools/providers/linguist.py) — system
   PATH first, then `<deps>/x64-windows/tools/Qt6/bin/lrelease.exe`).

```bash
python bootstrap.py translate
```

Re-run this whenever new `qsTr` / `tr` strings are added or existing
ones change. The build doesn't gate on it — fresh checkouts compile
without `.qm` files (the `translations.qrc` is included only when all
three `.qm`s exist; `BL_HAS_TRANSLATIONS` guards `Q_INIT_RESOURCE`),
and the runtime falls back to source strings.

### CMake bundling

[CMakeLists.txt](../../CMakeLists.txt)

```cmake
set(_LIBRARY_QM_FILES
    ${CMAKE_CURRENT_SOURCE_DIR}/translations/library_en.qm
    ${CMAKE_CURRENT_SOURCE_DIR}/translations/library_ru.qm
    ${CMAKE_CURRENT_SOURCE_DIR}/translations/library_uk.qm
)
# ...
if(_LIBRARY_QM_ALL_PRESENT)
    target_sources(BeeLibraryCore PRIVATE translations/translations.qrc)
    target_compile_definitions(BeeLibraryCore PUBLIC BL_HAS_TRANSLATIONS)
endif()
```

`main.cpp` mirrors the guard:

```cpp
#ifdef BL_HAS_TRANSLATIONS
  Q_INIT_RESOURCE(translations);
#endif
```

`Q_INIT_RESOURCE` is needed because `translations.qrc` lives in the
static library (`BeeLibraryCore`); without an explicit reference the
linker may strip it.

## Tests

### C++ — `LanguageModelTest` (Qt Test)

[src/tests/models/LanguageModelTest.cpp](../../src/tests/models/LanguageModelTest.cpp)

Run alongside the rest of the C++ test suite:

```bash
python bootstrap.py test
ctest --test-dir build/debug -V -R LanguageModel
```

Covered scenarios:

| Test | What it verifies |
|------|------------------|
| `availableCodes_returnsAllThreeInOrder` | `available()` exposes English/Russian/Ukrainian in stable enum order |
| `labels_areNonEmptyForEveryCode` | `label(code)` is populated for every supported code |
| `localeCode_matchesExpectedTwoLetterTag` | Two-letter ISO tags `en` / `ru` / `uk` |
| `initialState_withNoPersistedValue_isValidCode` | First-launch fallback to `QLocale` lands on a supported code |
| `initialState_withPersistedValue_restoresIt` | Existing `QSettings ui/language` is read back on construction |
| `initialState_withOutOfRangePersistedValue_clampsToValidCode` | Garbage / corrupt persisted values are clamped to a real enum value |
| `setCurrent_emitsCurrentChangedOnce` | Property setter emits exactly once per real change |
| `setCurrent_sameValue_doesNotEmit` | Setter is a no-op when value is unchanged (no spurious retranslate) |
| `setCurrent_persistsToQSettings` | Setter writes to `QSettings ui/language`, survives instance recreation |
| `applyCurrent_doesNotCrashWhenQmMissing` | Missing `.qm` is logged but does not abort the app (fresh-clone path) |
| `applyCurrent_isIdempotent` | Calling `applyCurrent` repeatedly with the same code is safe |

`QStandardPaths::setTestModeEnabled(true)` redirects `QSettings` to a
temp location, so the test never touches the user's real
`HKCU\Software\DarieszzBooks` (or its Linux/macOS equivalent).

### Python — `test_translate.py` (stdlib `unittest`)

[buildtools/tests/test_translate.py](../../buildtools/tests/test_translate.py)

```bash
python -m unittest discover buildtools/tests
```

No external dependencies — no `deep-translator`, no `lrelease`, no
network. Covered scenarios:

| Group | Tests |
|-------|-------|
| Regex (`_TR_RE`) | simple `qsTr`, disambiguation comment, plural argument, escaped quote, `QT_TR_NOOP`, `\b` word-boundary discipline (`subTr` / `mytr` reject), multiple matches per line |
| `_decode` | `\n`, `\"`, `\\` and plain-text round-trip |
| `_cpp_context` | namespace + class, split-form `namespace bl { namespace models { ...` , no-class fallback to filename stem, no-namespace bare class |
| `_qml_context` | basename-without-extension regardless of nesting |
| Placeholder protection | round-trip of `%1`, multiple `%1/%2/%3`, `%n` + `%L1`, deformed `@@ PH 0 @@` sentinels, no-placeholder pass-through |
| `_read_existing` | missing-file safety, finished translations preserved, `type="unfinished"` skipped, `<numerusform>` lists captured |
| `_write_ts` | well-formed Qt-Linguist XML, write→read round-trip, `type="unfinished"` for missing translations, `numerus="yes"` for plural messages, special-char escaping (`<`, `>`, `&`, `"`) |
| Integration | `_scan_sources` over a temp project tree captures C++ `tr()` and QML `qsTr()` (incl. plural marker) into the right contexts |

Auto-translation (the `_Translator` Google call) and `lrelease`
invocation are intentionally *not* covered — they hit external services
and binaries.

## Adding a new language

1. Append a value to the `Code` enum in `LanguageModel.hpp` (don't
   reorder existing values — they're persisted as ints in `QSettings`).
2. Extend `localeCodeFor(code)` and `labelFor(code)` in
   [LanguageModel.cpp](../../src/models/settings/LanguageModel.cpp) with
   the locale string and display label.
3. Update `LanguageModel::clamp` upper bound and `available()` list.
4. Add the new code to `TranslateCommand.LANGUAGES` in
   [translate.py](../../buildtools/commands/translate.py) and to
   `_LANGUAGE_TAGS` (locale tag like `"de_DE"`) and
   `_LRELEASE_NUMERUS_FORMS` (plural-form count for the language).
5. Add `library_<code>.qm` to
   [translations/translations.qrc](../../translations/translations.qrc).
6. Add the same path to the `_LIBRARY_QM_FILES` guard list in
   `CMakeLists.txt` (so the qrc is only attached when the new `.qm`
   has been generated).
7. Run `python bootstrap.py translate` — the new `.ts`/`.qm` pair gets
   auto-generated.
